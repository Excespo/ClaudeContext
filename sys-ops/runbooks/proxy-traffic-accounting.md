# Shadowrocket 流量与机场后台对账

## 对得上的是哪个数

**Proxy 一栏的「上传 + 下载」之和**；Direct 完全不计入机场统计。置信度 0.9。

## 四个系统性偏差

| 来源 | 量级 |
|---|---|
| **节点倍率** | IEPL/专线、流媒体解锁节点常设 1.5x/2x/3x。机场扣量 = Proxy 流量 × 倍率。最大的单一误差源 |
| 协议开销 | 机场统计的是服务器网卡进出字节，含 TLS 记录层、VMess/Trojan 头、TCP 重传、UDP over TCP 封装。实测差 5%~15%，机场侧偏大 |
| 多设备 | 机场 usage 是同一订阅下所有设备之和 |
| 上报延迟 | XrayR/sing-box 通常 60~120 秒批量上报一次 |

## 界面上最容易踩的坑

**流量计数器不随隧道重连归零**，只有手动重置或重装才清；而「开始时间 / 连接时间」只描述当前这一次连接。两者**不是同一个时间基准**，于是会出现「40 分钟用了 400G」这种不可能的读数。

一致性自检：上行合计 + 下行合计 ≈ 全部。若三者能对齐，说明「全部/代理/直连」是同一本账的三种切分，不是某一栏跑飞——那就是计数区间跨越了多次会话。

另一个可用信号：日常浏览的上下行比典型是 10:1~20:1。若代理栏出现 130:1，要么是长期流媒体/大文件走了代理，要么是规则把某类国内流量误判进了 PROXY。

## 校准方法

1. 在 ⋯ 里清空统计（并打开「启用存档」，之后可按天分段，不用再猜）
2. 只保留一台设备联网，下载一个已知大小的文件
3. 等两分钟看机场后台增量

算出的比值就是「倍率 × 开销系数」。接近 2.0 或 3.0 → 是倍率在起作用，不是开销。

## 已知坑

- 老的 `shadowsocks 2.8.2`（Python 版）在 OpenSSL 3 上启动失败：`EVP_CIPHER_CTX_cleanup` 在 OpenSSL 1.1.0 后已改名 `EVP_CIPHER_CTX_reset`。改源码能跑，但正解是换 `shadowsocks-libev`（CentOS/RHEL 需先装 EPEL）
