五个位置，各写什么

Project 页面上有四个面板加一份云端记忆，职责完全不同。写错位置的后果不是报错，是「看起来配好了但没生效」。

位置该放什么本地对应文件更新方式
Instructions角色、回答协议、禁止项、ladder。每轮对话都会生效，是真正的行为契约。<方向>/project-instructions.md改本地 → 粘贴覆盖
Description一句话说明这个 project 是什么。给人看的，不承担协议。README.md 表格很少改
Context（知识库）蒸馏后的 notes 与 00-index.md。不放原始代码和长文档。<方向>/notes/**快照上传，不会自动同步
MemoryClaude 自己在这个 project 里攒的上下文。几次对话后才出现，不用手动填。—自动
Scheduledproject 内的定期任务。与下面三个跑在 Cowork 的任务是两套东西。—按需
已经修过的一个错：四个 project 的协议最初写进了 Description，现在已迁到 Instructions，Description 只留一句话。以后改协议只动 Instructions。

信息的流向

新信息怎么进来

三条路径，按「材料在哪」选，不是按心情选。

在 chat 里聊出了结论 最常见

对话结束前让 Claude 把结论压成一篇 note，你存盘，而不是让它躺在聊天记录里。

把刚才这段压成一篇 note：机制 / 代码定位（file:line + commit）/ 数字 / 未解决问题，四段，不要复述文档，只写读了源码才知道的部分。再给我该加进 00-index.md 的那一行。

存到 notes/<domain>/<topic>.md，在 00-index.md 补一行，去 inbox 划掉对应条目。

材料在本机 Cowork

像现在这样挂着 ClaudeContext 文件夹的会话，可以直接让我读写文件，不用你来回复制粘贴。

读 ai-infra/inbox.md 里 serving 组的两条，对着 repos/vllm 把结论写成 notes/serving/paged-attention.md，然后更新 00-index.md 并把 inbox 那两行划掉。

适合批量整理、跨文件改动、要跑脚本验证数字的场合。

要读大型源码 Claude Code

repos/ 下的上游仓库不进任何知识库，留在本地按需 grep。蒸馏这一步才是真正产生理解的地方。

在 repos/Megatron-LM 里找到 TP 的 all-reduce 调用点，给我调用链和每步的通信量，标上 commit；结论按 note 四段式写到 notes/comm/ 下。

写完回到 chat Project 提问、被出题、被反驳。

上传知识库的几条机械规则

  • Context 是快照，不是同步。本地改了 notes，云端那份还是旧的——重新上传，并把旧文件删掉，否则同一篇笔记两个版本同时被检索到，回答会自相矛盾。
  • 只传 notes/** 与 ROADMAP.md。Instructions 里写了「先查 00-index.md」，所以 00-index 必须在；inbox.md 是你的待办，不必上传；repos/、sources/、experiments/ 一律不传。
  • 一个方向控制在几十篇以内。知识库接近上限会切到 RAG 检索模式，召回变模糊。宁可把三篇零散笔记合成一篇，也不要堆数量。
  • 命名即检索。文件名用 <domain>/<机制名>.md（如 comm/nccl-ring-allreduce.md），不要用日期或「笔记1」。
  • Instructions 里写的路径要和现实一致。如果以后把目录搬走或改名，四份 Instructions 都要跟着改，否则 Claude 会引用一个不存在的索引。

已经替你上好的三个闹钟

任务时间（北京）它会做什么产物
知识库体检周一 09:00统计各方向 notes 数量、最近改动天数、inbox 剩余、ROADMAP 进度；超过 21 天没动就点名。连续 3 次疏远会直接建议降级或合并该方向。STATUS.md + 推送
自测出题周五 20:00按 ROADMAP 当前阶段出 3 道题：推导、数字估算、源码定位。答案和判分标准折叠在题下。notes 还空的时候，改问 inbox 里那些「你以为懂了」的条目。对话 + 推送
归档巡检每月 1 日 10:00扫最近 35 天的新 chat，分流进各方向 inbox 的「待确认」小节，并报告是否出现了值得单开方向的新主题簇（同类 ≥5 条）。inbox 追加 + 推送
调整方式：直接在对话里说「把自测改成两周一次」或「停掉归档巡检」即可，不用自己去找设置。巡检只往 inbox 末尾追加「待确认」小节，不会动你手写的表格行。

交接清单：每个文件负责什么

这一节是写给以后的：无论是几个月后的你，还是一个没有本次上下文的 Claude 会话，读完这张表就能接手。

文件职责不变量
README.md方向清单与共同约定增删方向必须先改这里，定期任务以它为准
<方向>/CLAUDE.md给 Claude Code 的项目记忆控制在 200 行内；路径作用域规则放 .claude/rules/
<方向>/project-instructions.md云端 Project 的 Instructions 原文本地是真相源，云端是副本
<方向>/ROADMAP.md阶段与当前状态唯一状态文件，别在别处重复写进度
<方向>/notes/00-index.mdtopic → note → 源码定位 → 掌握度新建 note 必须同步登记，否则等于没写
<方向>/inbox.md待蒸馏队列只减不增地推进；每条都带一个具体问题，不是标题堆
mac-ops/inventory.md设备与卷的唯一事实源回答涉及具体卷时先查它，不要假设设备号
STATUS.md最近一次体检结果机器生成，随时可覆盖，不要手写内容进去

四个红旗

把整个 repo 传进知识库

vLLM 这种体量进去之后检索会退化成模糊语义搜索，回答开始编造文件名。源码留在 repos/，让 Claude Code 按需读。

把 chat 当笔记本

结论留在对话里 = 三个月后找不到。判据很简单：如果一个结论没有对应的 notes 文件，就当它不存在。

inbox 只进不出

归档巡检会持续往里加。如果连续两次体检 inbox 剩余数没下降，说明产能不够，该砍方向而不是继续攒。

机器状态写进全局配置

外置盘、卷名、网盘这类本机事实属于 mac-ops/inventory.md，不属于全局 CLAUDE.md，更不属于账号级 preferences——那里只放「你希望 Claude 怎么回答」。

接下来这一周

  1. 把 ai-infra 的 Instructions 里那两行路径核对一遍确认 ~/Codes/ClaudeContext/ai-infra/notes/ 和你实际的大小写一致（磁盘上是 codes，Mac 不区分大小写，但以后同步到别处会区分）。
  2. 做第一次蒸馏，只做一条从 inbox 的 serving 组挑「Accelerate 与 vLLM 的显存管理」，把 KV cache 显存账算出来，写成第一篇 note。第一篇写完，这套目录才算活了。
  3. 把这一篇 note 和 00-index.md 上传到 AI-Infra 的 Context然后在那个 project 里问一个你已经知道答案的问题，验证它确实读到了索引——这是唯一能确认「上传生效」的方法。
  4. 周一早上看体检报告那时四个方向都会显示「0 篇 notes」，这是基线。往后每周看的是斜率，不是绝对值。
